# 徽派家私项目测试与 AI 落地方案

## 1. 目标

本项目不是做一个“会聊天的测试助手”，而是建立一个可复用的闭环：

`变更输入 -> 测试点生成 -> 用例执行 -> 缺陷归因 -> 测试报告 -> 回归资产沉淀`

AI 在这里承担的是辅助分析和加速生成，不替代测试结论和上线决策。

## 2. 当前项目的测试对象

基于当前仓库，核心测试对象如下：

| 业务域 | 前端页面 | 后端接口 | 典型风险 |
| --- | --- | --- | --- |
| 阶段模板 | `StageConfig.vue` | `/api/stage/list/create/update/delete` | 树层级错误、长名称遮挡、删除约束 |
| 成本阶段模板 | `ProjectCostConfig.vue` | `/api/cost-stage/list/create/update/delete` | 预算标准录入、节点排序、删除约束 |
| 预算管理 | `ProjectBudgetManagement.vue` | `/api/project-budget/list/create/update/delete` | 金额显示、成本项重排、重复记录、状态计算 |
| 进度管理 | `ProjectProgressManagement.vue` | `/api/progress/list/create/update/delete/upload` | 批次同步、节点重排、执行人归一化 |
| 执行工作台 | `ProjectExecution.vue` | `/api/progress/list`、`/api/user/list` | 当前用户过滤、超期原因、移动端展示 |
| 发货管理 | `DeliveryManagement.vue` | `/api/delivery/list/create/update/delete/upload` | 单据状态、附件、异常发货 |
| 检测交付 | `InspectionDeliveryManagement.vue`、`InspectionDeliveryMobile.vue` | `/api/inspection-delivery/list/update` | 交付状态、异常回填、项目经理通知 |
| 看板 | `Workbench.vue`、`OverallBudgetDashboard.vue`、`ProjectControlDashboard.vue` | 聚合预算/进度/交付数据 | 汇总指标和图表口径不一致 |

## 3. AI 在本项目里的实际落点

### 3.1 需求或变更转测试点

输入：

- 产品需求文档
- 设计原型
- 变更代码文件
- 最近缺陷记录

输出：

- 模块受影响范围
- 新增测试点
- 回归最小集

最适合本项目的变更输入源：

- `frontend/src/pages/StageConfig.vue`
- `frontend/src/pages/ProjectCostConfig.vue`
- `frontend/src/pages/ProjectBudgetManagement.vue`
- `frontend/src/pages/ProjectProgressManagement.vue`
- `backend/api/project_budget.py`
- `backend/api/project_progress.py`
- `backend/api/inspection_delivery.py`

### 3.2 用例补全和去重

AI 可用于：

- 按页面和接口字段补边界值
- 从缺陷反推漏测场景
- 将重复用例合并成标准模板

例如预算管理模块，AI 应重点补充：

- 金额显示的小数和千分位
- 成本项编辑时默认值回填
- 删除后序号自动重排
- 重复成本项拦截
- 汇总行和明细行数据一致性

### 3.3 执行失败归因

执行测试后，把以下材料统一交给 AI：

- 失败步骤
- 接口返回体
- 控制台报错
- 页面截图
- 本次提交 diff

AI 产出：

- 失败摘要
- 疑似根因
- 影响范围
- 是否建议阻塞上线
- 缺陷单草稿

### 3.4 自动生成测试报告

AI 最适合处理报告中的高噪声文本，包括：

- 回归结果汇总
- 风险归纳
- 缺陷分类
- 版本结论草稿

测试负责人只需要审核结论，不需要每次从零手写周报和版本报告。

## 4. 推荐的落地流程

### 4.1 提测前

1. 收集本次变更文件。
2. 用 AI 识别受影响模块。
3. 从现有用例库中筛选基础回归用例。
4. 由 AI 补充版本特有测试点。
5. 测试负责人确认最终执行集。

### 4.2 执行中

1. 手工执行核心业务链路。
2. 对接口、控制台、页面截图进行留证。
3. 将失败证据交给 AI 生成缺陷草稿。
4. 测试人员审核后提交缺陷系统。

### 4.3 执行后

1. 汇总通过率、阻塞问题、遗留风险。
2. 用 AI 生成日报或版本报告初稿。
3. 把本次新增缺陷反向补到用例库。
4. 把典型问题补进 AI 提示词和回归知识库。

## 5. 首批实施范围

建议先做 3 个试点模块：

| 优先级 | 模块 | 原因 | 首批成果 |
| --- | --- | --- | --- |
| P0 | 项目预算管理 | 业务计算最复杂，线上口径风险最高 | 用例集、回归清单、报告模板、缺陷提示词 |
| P1 | 项目进度管理 | 节点重排和批次逻辑复杂 | 变更影响分析、节点回归用例 |
| P1 | 检测交付管理 | 跨发货、项目经理、移动端多个对象 | 交付状态用例、异常通知用例 |

## 6. 建议的角色分工

| 角色 | 责任 |
| --- | --- |
| 产品/项目经理 | 提供版本变更清单和业务验收标准 |
| 测试负责人 | 审核 AI 生成的测试点、决定执行范围、确认结论 |
| 开发 | 提供接口说明、异常日志、变更说明 |
| AI 工具 | 生成测试点、补齐用例、总结失败、输出报告草稿 |

## 7. 测试资产字段标准

无论后续放在 Excel、禅道、Jira 还是 Markdown，建议统一字段：

| 字段 | 说明 |
| --- | --- |
| 用例编号 | 如 `BUD-03` |
| 模块 | 如 `项目预算管理` |
| 需求来源 | 需求编号、问题单、改动说明 |
| 前置条件 | 项目、账号、测试数据 |
| 测试步骤 | 保持可执行、可复现 |
| 预期结果 | 结果必须可验证 |
| 优先级 | `P0/P1/P2` |
| 回归标签 | 冒烟、回归、发布前、线上问题回归 |
| 关联缺陷 | 历史问题编号 |

## 8. 本项目 AI 知识库建议

建议建立 3 类知识库数据：

### 8.1 用例知识库

- 模块
- 用例编号
- 前置条件
- 测试步骤
- 预期结果
- 是否自动化

### 8.2 缺陷知识库

- 缺陷标题
- 发现日期
- 发现版本
- 模块
- 根因
- 修复文件
- 是否需要回归

### 8.3 报告知识库

- 版本号
- 执行时间
- 执行人
- 覆盖模块
- 通过率
- 阻塞项
- 风险项

## 9. 验收指标

首批落地建议用以下指标衡量：

| 指标 | 目标 |
| --- | --- |
| 用例补全效率 | 测试点整理耗时下降 30% 以上 |
| 报告产出效率 | 日报或版本报告编写耗时下降 50% 以上 |
| 缺陷描述质量 | 缺陷单一次性补充率提升 |
| 回归遗漏率 | 同类问题重复出现频率下降 |

## 10. 近期可直接纳入知识库的样例问题

以下问题建议作为首批 AI 学习样本沉淀：

- 阶段节点结构中子节点不应继续新增子子节点。
- 阶段节点名称过长时删除按钮不可点击。
- 预算管理编辑成本项时，应默认回填本行成本项。
- 预算管理金额显示应保留两位小数，且不能对浮点误差的小数部分错误插入千分位。

这些样例既适合作为回归测试点，也适合作为 AI 生成报告和缺陷归因的参考案例。
